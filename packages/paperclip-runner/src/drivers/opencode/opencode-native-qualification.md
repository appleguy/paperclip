# OpenCode 2 native qualification

The Homebrew executable reports `opencode v2.2.5`; `serve --help` identifies a v2 API. This does not identify the version or ownership of an already running background service. Runner currently pins `opencode-ai@1.18.34`, spawns its own isolated server, and expects v1 `/global/health`, `/session/...` and `/event` APIs. It does not attach to a shared v2 service.

The upstream [v2.2.5 session protocol](https://github.com/anomalyco/opencode/blob/v2.2.5/packages/protocol/src/groups/session.ts) defines `POST /api/session/:sessionID/prompt` and experimental `GET /api/experimental/session/:sessionID/log`, whose `after` is an exclusive aggregate sequence and `follow=true` enables replay followed by live events. The [event schema](https://github.com/anomalyco/opencode/blob/v2.2.5/packages/schema/src/event.ts) binds the sequence to `durable.aggregateID`; the [synchronization marker](https://github.com/anomalyco/opencode/blob/v2.2.5/packages/schema/src/event-log.ts) marks the captured replay watermark. The [session contract](https://github.com/anomalyco/opencode/blob/v2.2.5/specs/v2/session.md) explicitly distinguishes the session log from the instance live stream, which has no replay guarantee. Session IDs and message IDs are meaningful idempotency identities; process-local execution is not proof of durable ownership.

The offline test checks only that the existing SSE frame parser preserves representative v2 durable and synchronization frames across fragmented input. It does not establish event semantic compatibility, live server authentication, cursor persistence, single-writer fencing, or native session attachment. The v1 driver must not be pointed at v2 by merely changing its paths or relaxing the version check: prompt payloads, event vocabulary, session-scoped replay and process ownership require a separately integrated v2 transport. The log endpoint is experimental and must be version-qualified.

Existing `pcctx` exposes separate read, watch, send and reconcile commands; that is not evidence that Runner uses the same mutation ingress. Herdr/Moshi have v2 integration in the existing host implementation, including session-scoped event handling, but their UI/relay does not establish Runner replay or write ownership. No server, model, TUI, credentials or live database was changed during this qualification.

An opt-in `OpenCodeV2Shared` transport now implements the qualified session read, prompt and durable-log HTTP shapes. It is not wired to a production caller. Its required caller-owned authority must independently attest the authenticated server version and process generation, serialize competing Runner mutations, while observing owner-originated mutations without blocking them, persist operation identities and digests before sending, and atomically apply observed log items with cursor updates. An in-memory implementation is not sufficient. A lost prompt acknowledgment can be retried with the same message ID only under that durable admission contract. Owner or other client activity is observable in the log and is not attributed to Runner.

The tagged server handler delegates the session log directly to the session service; its upstream tests exercise a `log.synced` marker, exclusive `after`, and gaps in public sequences. This client requires an Authorization header, snapshots caller headers, rejects non-JSON session/prompt responses, bounds prompt and JSON sizes, and refuses truncated durable frames. Stream disconnection is reported to the caller; a new call loads the last atomically committed cursor. An existing OpenCode PRP event queue/checkpoint is not an atomic provider-log cursor and generation authority, so it cannot safely instantiate this transport without additional server-owned integration.

## Existing PRP integration boundary

The Runner durable control plane calls its business `onCommittedEvent` before saving its own acknowledgment cursor (`src/control-plane/durable-prp-control-plane.ts`, event handling around line 3720). This correctly permits idempotent replay of Runner events, but that cursor is Runner `sourceSeq`, not an OpenCode aggregate sequence. Its bounded committed-event window and checkpoint filtering do not preserve every provider-log item. Rust's executor-event deduplication receipts are bounded to 256. Neither is an authoritative, indefinitely recoverable OpenCode cursor or a transaction joining an OpenCode event to its projection.

The server's `providerSessionIdentityFromDurableProviderState` OpenCode branch verifies existing provider state and session IDs but does not bind an authenticated shared backend generation or persist its v2 aggregate cursor. A concrete caller needs a server-owned durable transaction that validates the active run/lease and backend generation, idempotently persists each exact OpenCode item and its aggregate cursor together, and records message ID plus payload digest before dispatch. It must reconcile external turns and gate only competing automated writes. Those server/PRP changes and an attested backend credential handle are not present in the driver-only surface. A separate driver-side journal would not establish the required server lease or atomicity, so none was created.

Read-only process/listener inspection found simultaneously running installations from 2.0.32 and 2.2.2 and a Homebrew 2.2.5 process. This does not identify which is the authorized shared backend or establish its authentication or generation. No backend request, credential or database was accessed.
